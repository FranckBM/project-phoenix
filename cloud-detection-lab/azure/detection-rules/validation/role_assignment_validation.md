# Validation: Entra ID Directory Role Assigned to User (T1098.003)

**Rule file:** `entra_role_assignment.yml`
**Data source:** Entra ID audit logs (Microsoft Graph `/auditLogs/directoryAudits`), ingested by `ingest_entra_audit.py` into `logs-azure.entra_audit-default`
**Validated:** 28 Oct 2026
**Result:** ✅ Positive test alerted once; negative test did not alert

---

## 1. What the rule detects

A successful assignment of a Microsoft Entra ID **directory role** to a principal. Adding a principal to a role is a common privilege escalation and persistence step after an identity compromise.

- **ATT&CK:** Persistence (TA0003) and Privilege Escalation (TA0004) → Account Manipulation: Additional Cloud Roles (T1098.003)
- **Query (KQL):** `event.action:"Add member to role" and event.outcome:"success"`

## 2. Telemetry: what the event looks like

The event was generated by assigning **Security Reader** to the test user at directory level (Entra admin center → Roles and administrators). Relevant fields, redacted:

| Field | Value |
| --- | --- |
| `event.action` | `Add member to role` (plain ASCII, no dash) |
| `entra.audit.category` | `RoleManagement` |
| `entra.audit.operationType` | `Assign` |
| `event.outcome` | `success` |
| `user.name` (actor) | admin UPN, from `initiatedBy.user.userPrincipalName` |
| `entra.audit.targetResources[0].userPrincipalName` (target) | test user UPN |
| `entra.audit.targetResources[0].modifiedProperties` | `Role.DisplayName` = `"Security Reader"`, `Role.TemplateId` = `"5d6b6bb7-de71-4623-b4af-96380a352509"`, `Role.ObjectID`, `Role.WellKnownObjectName` |

**Notes on the data**

- `modifiedProperties.newValue` values carry **literal double quotes** (`"\"Security Reader\""`). An exact `term` query including the quotes matches; queries without them will not.
- The **target** principal has no ECS field. It only exists inside `targetResources`, so it is listed as an investigation field.
- `Role.TemplateId` is a stable, language-independent GUID. It is the better field to match if the rule is ever scoped to privileged roles only.

## 5. Detection latency (single observation)

| Stage | Time |
| --- | --- |
| Event → ingest (`@timestamp` → `event.created`) | ~2m37s |
| Ingest → alert (`event.created` → alert `@timestamp` 12:17:05.803) | ~1m23s |
| **End to end** | **~4m00s** |

Event-to-ingest covers Graph audit log availability plus up to 120 s of polling. Ingest-to-alert depends on where the event lands in the 5-minute schedule. This is one observation, not an average. For comparison, the Entra credentials rule measured ~5m32s end to end.

## 6. Design decisions

- **No alert suppression.** Suppressing by actor (`user.name`) for 1 hour would fold a later, more dangerous assignment (for example Global Administrator) into an earlier low-privilege alert from the same admin, hiding the escalation the rule exists to catch. Directory role assignments are rare enough that alerting on each one is cheap.
- **All roles, not only privileged ones.** Medium severity covers every directory role. A High-severity variant scoped to privileged `Role.TemplateId`s (Global Administrator, Privileged Role Administrator, etc.) is a possible follow-up.
- **Removals are excluded.** `Remove member from role` is a separate action and does not match. Unlike the credentials-changed rule, this rule cleanly separates additions from removals.

## 7. False positives and tuning

- Legitimate administrator role assignments: onboarding, delegation, break-glass setup.
- Tuning options in a real tenant: exclude known provisioning identities by `user.name`, or raise severity only for privileged role template IDs.

## 8. Limitations

- **Free tenant, no PIM.** Assignments are permanent and active immediately. With Entra ID P2, PIM eligible assignments and activations log different events, which this rule does not cover.
- **App-scoped role assignments** (roles scoped to a single app registration) were not tested.
- **Ingest dependency.** Detection depends on the Python ingest script running. If it stops for longer than the tenant's audit log retention, events are lost.

## 9. Investigation and response

**Investigate:** Who made the assignment (`user.name`), to whom (`targetResources.userPrincipalName`), which role (`Role.DisplayName`), from where (`initiatedBy.user.ipAddress`, `additionalDetails` User-Agent), and was it expected (change ticket, onboarding)? Check the actor's recent sign-in and audit activity.

**Respond:** If unauthorised, remove the role assignment, revoke the target's sessions, review the actor account for compromise, and reset credentials as needed.
